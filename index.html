    Part IChapter 00

    背景

    xlsx 是二进制，SVN 文本合并直接失效；而策划表恰恰改动最频繁、跨分支需求最强。

    为什么不能用 SVN merge

    • xlsx 是 zip，改一格整个字节流全变 → 只能报「整文件冲突」。
    • 行号不是身份，ID 才是。同一条数据在两个分支行号不同，列序也会被随手拖动。
    • 分支链长：trunk → stable → publish，还有 bjs / pre / global 旁支。
    • 误合一行数值 = 一次线上事故。

    把 xlsx 还原成 「行 ID × 列 ID → 值」 的语义模型，在模型上做三路合并，再写回物理表格。字节层的 diff 全程不参与。

    四个输入版本

    角色来源用途
    base源分支 r-1算 diff 的基准
    source源分支 r决定「哪里改了」
    trunk源分支 HEAD决定「改成什么值」
    stable目标分支 HEAD唯一被修改与保存的对象

    base→source 定位改动，trunk HEAD 提供取值。
    只有 trunk 上该行/列已不存在时，才退回用 source 兜底。

    Part IChapter 02

    入口：POPO 监听器

    用户不碰 Jenkins，也不碰 SVN，只在 POPO 里发一句话。

    /发起merge 来源分支： trunk  目标分支： stable  单号列表： 11111, 22222
后缀：dev_skip（跳过预检）  fake_user=xxx（代发）

    用户只给单号，合并类型由机器人自己认。

    拉取单号下的全部提交文件 → path_classifier 按路径归类 → 得到该单号涉及的所有 merge 类型（策划表 / 动画 / 音效 / UI / 场景 / 代码 …）。 一个单号横跨多个类型时，确认卡上一次性列出，点一下同时发起全部类型，各类型走各自的 Jenkins job。

    预检五步

    1 格式单号必须全数字
    2 拉文件compass + 分支过滤
    3 分类path_classifier
    4 本地校验分支限制
    5 Robot类型可行性

    任一步失败 → 失败卡片（按类型分组原因）；全通过 → 确认卡片。

    三个非平凡问题

    A预检慢，用户以为机器人挂了

    解法
    立即回一句「查询中…」（引用原消息，多人并发不串），真正工作丢进 daemon 线程。

    B卡片超长被 POPO 拒收

    解法
    _split_refs_into_chunks() 双硬限制贪心分片：单卡 ≤15 单号 且 文件列表 ≤6000 字符。文件列表预取复用，不重复请求 compass。

    C预检失败的类型被 auto-detect 重新带上

    根因
    卡片只传单号不传「允许哪些类型」，回调侧只能重新自动检测。
    解法
    按 frozenset(passed_types) 聚类发卡，部分失败的簇显式带 option_type，回调侧据此过滤。
    灰度 确认卡发出后无法再改，检测到灰度提交时追发一条独立消息用「↑↑↑」指向上方卡片。

    代码：handlers/command_initiate_merge.py、parsers/initiate_merge_parser.py

    Part IChapter 03

    卡片回调服务

    要在 POPO 苛刻的超时窗口内返回，还要保证手抖点两下不会 merge 两次。

    1 校验SHA-256 签名 + AES 解密
    2 路由按 actionType 查表
    3 幂等uuid TTL 60s
    4 秒回DATA_UPDATE 改按钮
    5 异步线程内触发 + 回写进度
    actionType行为
    ACTION_CONFIRM幂等 → type→refs → 分支流向校验 → 逐类型触发 → 进度回写
    ACTION_CANCEL卡片置「已取消」，折叠详情
    ACTION_MUTE从提醒队列删除该 ref
    ACTION_REVIEWwarn 卡确认 → 回写 Stats 已读状态

    D重复点击触发两次 merge

    解法
    以 instanceUuid 做 TTL 60s 幂等锁。没抢到锁不报错，返回和首次一样的卡片态，用户无感。

    E回调超时，卡片卡在旧状态

    解法
    响应与执行分离：先秒回「发起中…」，daemon 线程每完成一个类型就 PUT 回写 callback_percent，全部完成写终态，失败额外发私聊。

    F分支拼错，跑到 Jenkins 才失败

    解法
    触发前查 is_valid_merge_flow()，读的是和合并引擎同一份 DEFAULT_TYPE_DCT。不合法直接改卡片文案，零 Jenkins 请求。

    失败提醒指数退避重发，三种情况清除：用户 mute / 该 ref 被成功触发 / 部分成功时只清成功类型。

    代码：card_callback_server/app/handlers.py、utils/idempotency.py

    Part IChapter 04

    确认闭环与待办提醒

    合并跑完只是一半。有人真的去看了那份 diff，才算完。

    问题 卡片发出去了，警告也列清楚了 —— 然后沉进聊天记录。 等到策划发现数值不对，已经是三天后。

    点一下，闭环就成了

    卡片就地变样，不再发一条新消息。点过的和没点的，扫一眼聊天窗口就分得清。

    回调返回的 DATA_UPDATE 同时把两个折叠面板收起来 —— 已经看完的东西不用再占屏幕。

    没点的，每天提醒两次

    10:30 和 16:35，各扫一遍 reports 表。

    这条过滤挡掉什么理由
    不在最近 1 小时内刚合完就催，人还没走到工位
    只看两周内再老的单子已经失去确认价值，纠缠只剩噪音
    发起人是纯数字群号，群里没有「指派人」这个概念
    指派人已在 confirmed确认按人记，同一单别人确认过不算他确认过

    收件人取的是 Redmine 指派人，不是发起人。发起人往往是工具组的人，真正该看数据的是策划本人。

    !一张卡装多个单号，uuid 没地方放了

    起因
    提醒卡按人聚合，一张卡里可能有十几个单号。可 review_uuid 是卡片级变量，只有一个坑位。
    做法
    review_uuid 传空串，把 uuid 塞进每一行文本： 单号:123456, 时间:…, uuid:826ede65-…。哪一行被点，就带哪一行的内容回来。
    代价
    回调侧要同时认两种格式：老卡片传纯 UUID，新卡片传整行文本。 _extract_review_uuid() 用 8-4-4-4-12 正则从里面抠，抠不到就原样透传让下游报错。
    6k 上限 warn_content 超 6000 字节会被 POPO 拒收。按行累加，超了就停在上一行，剩下的留到下一个时间点 —— 反正一天有两次机会。

    卡片的 instanceUuid 每次新生成，不与任何 report uuid 绑定。 提醒卡是一次性广播，不需要像 warn 卡那样保持同一实例的连续性。

    代码：manager_design/stats_client.py（上报）·excel_merge/card_api.py（发卡）· card_callback_server/app/handlers.py _handle_action_review·stats/reminder_scheduler.py（每日扫描）

    Part IChapter 05

    分发与统计

    多机并行会互相踩 SVN 工作副本。分发器解决「谁跑什么」。

    旧做法 单号哈希取模分机器。取模不感知文件冲突：两个单号改同一张表被分到两台机器，后提交者覆盖前者。
    现做法 中心化分发 + 文件级冲突图。请求 JSON 带 committed_files，文件集合有交集的 ref 不允许同时在跑。

    三态本身是结果。真正的问题是：每一轮该从队列里捞哪几个出来跑。

    冲突图：每轮求一个极大独立集

    节点 = 一个待合并单号，边 = 两者的 committed_files 有交集。
    「一批能并行跑的单号」= 这张图上两两无边的一组点。

    三个实现要点

    要点做法
    不建邻接矩阵_build_file_to_refs() 建 file → ref_ids 反向索引，查邻居时只遍历自己那几个文件。两两求交是 O(n²) 次集合运算，反向索引摊到 O(总文件数)
    贪心的排序键(queued 优先, 冲突度↑, 文件数↑, 到达序)。先放冲突度低的，同一轮能塞进更多互不相交的 ref；queued 提到最前是防饿死
    依赖回填被挡下的 ref 记 dependencies = 冲突邻居 ∩ (assigned ∪ 本轮已选)。看板上能直接答「我在等谁」
    无死锁 只有已占用文件才能挡住候选。assigned 为空时不存在任何已占用文件，排序第一位必然入选 —— 队列不可能全员互相等待。
    依赖边也天然无环：只允许新 ref 依赖已有 ref，已有 ref 的 dependencies 从不回写。

    选中后 least_loaded_job() 按 assigned 中各 job 的当前计数取最低，同计数时保持 jobs 原顺序 —— 让分配结果可复现。

    G内存与磁盘漂移，单号永久卡死

    症状
    写完 assign 后 commit 失败被 revert：磁盘仍是 unassigned，内存已记 assigned → 既不重分配也不会完成。
    解法
    ① 启动时 bootstrap 重建内存态；② 定时 _reconcile_assigned_with_disk() 以磁盘为准校正。无法识别的值只告警不动内存。

    对账循环：机器健康 + 内存/磁盘一致性

    每 30 分钟一次对账 tick，把两样容易漂移的东西押回现实：机器的在线状态，和磁盘上的 ref 文件。

    三个落地要点

    要点做法
    job → 物理机 IPjenkins-ci 的 config.json 以 svn extern 挂进 stats/，node 字段取 "_" 前段；文件缺失直接跳过健康检查，调度不受影响
    在线判定系统 ping，输出含 TTL= 才算在线 —— Windows 上「不可达」也可能 returncode 0
    告警节奏离线、分支全挂各发一次 POPO（fully_blocked 去重）；恢复只记日志不打扰
    效果 机器掉线最多一个对账周期被发现：其上的 assigned ref 当场改派健康机器并触发新 job，新分配也不会再落入黑名单；机器恢复后自动解禁。

    完成度闭环

    一个单号跨多类型异步完成。Stats 维护 ref_status，每类型一列。

    未齐静默等待，不打扰
    全成功查 auto_drag 偏好 + Redmine 状态 → 自动拖单
    含警告只提醒，人工确认后手动拖
    并发 多 job 同时上报最后一个类型会重复通知。解法：先原子置 notified=1，再发通知——宁可漏发不重发。

    代码：stats/distributer/scheduler.py、stats/distributer/machine_health.py、stats/completion_checker.py

    Part IChapter 06

    out-of-date 与降级提交

    冲突图管的是事前排开。真撞上了，是另一码事。

    分发器只保证本批次内部互不相交。分支上还有策划、还有别的工具、还有别的 merge 类型 —— 这些人分发器管不着。

    旧做法 svn commit 报 E155011 / E160028 → 整个目录 revert，本次全部作废。 一次提交动辄几十个文件，别人只动了其中一张表，算好的几十个文件跟着一起白扔。
    现做法 降级提交：把真正撞车的文件挑出来退回队列，其余照常提交。

    怎么算 out-of-date

    svn st -qu

M       *     12345   道具表.xlsx      ← 本地改了 + 服务端更新了 = 真冲突
        *     12345   技能表.xlsx      ← 本地没改，不影响 commit

    判据是第 8 列为 * 且第 0 列非空。少了后半个条件，会把一大片「本地没动过」的文件误判成冲突， 降级直接退化成全量回滚。

    三处配套，少一处都出事

    位置少了会怎样
    real_run_merge
    有 OOD 就跳过 clear_info    		ref 被清出队列，那几个文件再也不会重试
    processNeedSetRefsToOk
    OOD 非空则不自动拖单    		活没干完，单子已经被拖到「已完成」
    ref_log / SUCCESS_PROCESS_FILE
    剔除被 revert 的文件    		数据永久丢失，且全程无报错 —— 见下

    !被 revert 的文件，被远端记成了「已合并」

    症状
    某张表的改动怎么都合不过去。重跑、重建单都没用，日志里一条报错都没有。
    根因
    _real_process_out_list 在每个文件操作成功的当下就写 ref_log，而 revert 发生在这之后。 create_ref_log 照着 ref_log 把这些文件 insert 到远端「已合并」服务 → 下次重试时它们被判定为已合并，直接 skip。
    解法
    降级成功后、return 之前，按相对路径把 OOD 文件从 ref_log 与 SUCCESS_PROCESS_FILE 里删干净。 用独立内层 try 包住：清理失败也照常返回，避免被外层 except 吞掉。

    另一种策略：灰度合并直接中止

    Design 主流程灰度合并
    一次提交几十个文件单个文件
    撞 OOD降级，保住其余中止整个 run
    ref 去向都留在队列，等下次 Jenkins

    单文件场景没有「保住大部分」可言，中止反而更简单可靠。同一个问题，规模不同，最优解就不同。

    从源头少撞车

    externals Design 分支大量使用 SVN externals（branch_trunk_bjs/design/1System 实际指向 trunk/design/1System）， 导致基类采集的 modify_files 恒为空，按文件冲突分配的逻辑整个失效。

    改法：跳过逐 ref 分配，在 _on_batch_add_complete 里把同批次 ref 统一按负载均衡分到同一台机器。 同机串行执行，天然不会自己跟自己抢。

    代码：design_manager.py commit_dir_add_info L1026 · svn_util.py get_out_of_date_files L709

    Part IChapter 07

    数据模型

    所有决策发生在语义模型上，不在 openpyxl 坐标上。

    两种表头格式

    格式 A（3 行）格式 B（4 行）
    第 1 行中文表头备注（不参与合并）
    第 2 行英文表头 ID中文表头
    第 3 行类型英文表头 ID
    第 4 行数据起始类型
    第 5 行—数据起始

    按类型行位置判定（首列为 id 列，类型一般是 str/int）。

    行 ID = 复合身份

    row_id = id @_@ branch_mark @_@ skip [ @_@ extra... ]

id           第一列的值
branch_mark  列不存在时默认 "trunk"
skip         列不存在时默认 "1"
extra        id_rules.json 针对特定 sheet 配置的额外 key 列

    有些表靠 id + 业务维度才唯一；不纳入行 ID 就会直接触发行 ID 查重失败。

    ID 列表头缺失的四象限

    trunkstable处理
    有有正常
    有无前置操作 2 先同步列，再走正常规则
    无有非 ID 单元格修改不写入，新增行 ID 照常写
    无无都取默认值

    列 ID

    = 英文表头，统一小写作 key，original_key 保留原写法。 不归一化则 ItemId 与 itemid 会被当两列，撑出重复列；写回时又必须用原写法，否则导表脚本找不到列。

    最大的坑 header.col_idx 不一定是物理列号——插列时可能是 7.5 这样的浮点排序值。 所有写入必须 find_phys_col() 按列名重新物理查找。
    Part IChapter 08

    流程概览

    一次合并 = 把 r-1 → r 的改动落到 stable。四个版本进，一个文件出。

    为什么把行列与单元格拆开

    每个阶段的出口立一条假设，下一阶段就建立在这条假设之上。

    阶段只负责因此下一阶段不必再操心
    P1列的集合P2/P3 不再判断「这一列该不该建」
    P2行的集合P3 不再判断「这一行该不该建」
    P3格子里的值四条规则只需回答一个问题：取谁的值

    耦合在一起写过一版：单元格规则里既要判断行在不在、又要顺手建行建列，边界情况呈组合爆炸。 拆开后 P3 的规则表从十几条塌缩成四条。

    贯穿全程的指导原则

    原则 能取 trunk 最新，就取 trunk 最新。只有 trunk 上这一行 / 这一列已经不存在了，才退而取中间版本 source(r)。

    这条原则贯穿前置操作 2（同步表头取 trunk）、前置操作 4（类型修复取 trunk）、单元格规则 (1)（主路径取 trunk）。

    它真正在防的东西：无序合并

    单号是并发提交、乱序合并的。r5 的单号可能比 r9 晚一周才轮到合并。

    陷阱 1 ID 复用　r5 删掉行 X，r7 又新建了一行 ID 同为 X 的数据。 此刻才去合并 r5 的那条删除 —— 删掉的是后来那一行，一条无辜的新数据凭空消失。
    陷阱 2 孤儿残留　r5 新增行 X，r9 删除行 X。先合 r9：stable 上压根没有 X，删除空转。 事后再合 r5：X 被加进 stable，而再也没有第二次删除来抵消它 —— 一行早该消失的数据永久留了下来。
    解法 两个陷阱的共同点：拿历史操作去改一个不知道走到哪一步的现状。 trunk 最新是所有操作叠加后的终态，与合并顺序无关。把它当仲裁人，顺序这个变量就消失了。

    落到规则上

    本次操作trunk 最新stable动作
    删除行 X还有 X有 X不删，建单转人工 —— trunk 都还留着，说明后来又加回来了
    已无 X有 X执行删除 —— 终态确实没有它
    新增行 X已无 X无 X不加，建单 —— 加进去就成了永久孤儿

    代价是把判断不了的情况交给人。宁可漏合，不可错合：漏了有人补，错了要翻整张表。

    规格：manager_design/GUIDE_EXCEL.md　实现：excel_merge/diff_merge_core.py

    前置操作

    对齐表结构。这条流水线的顺序本身就是设计。

    三条假设 = 三个守门检查

    假设被破坏时
    假设 1英文表头 ID 唯一列映射不确定 → high 单 + 跳过该表

    • 类型修复不立刻写盘，作为 type_repair_changes 传给 P3，按 (row_id, col_id) 去重后统一写。

    未来方向：操作来源与数据来源分离

    往 publish 合并时，源分支该选 stable 还是 bjs —— 这个问题目前没有正确答案。

    现状：一个 source 身兼两职

    职责当前取自要求
    操作（哪里改了）base r-1 → source r要贴近开发者的原始意图
    数据（改成什么值）同一分支的 HEAD要是已经过测试验证的值

    两个职责绑在同一个分支上，而它们想要的分支并不是同一个。

    取哪个分支都会输

    选 stable 当 source
    • 操作序列被漏合改写过
    • 表结构与 bjs 已分叉
    • 数值经过测试验证
    选 bjs 当 source
    • 操作序列 = 开发者原意
    • 数值未经测试

    方案：拆开取

    例子

    单号 #33012 在 bjs 上把 hp 从 100 改到 150，并新增一列 quality。stable 因为一次漏合，quality 列压根不存在，hp 则被测试同学回调到 120。现在要合进 publish。

    来源操作取值写进 publish
    当前做法（source = stable）stable 上无 quality 的新增记录 → 整列丢失120只改了 hp
    当前做法（source = bjs）加列 quality + 改 hp150（未测）把未测数值带进 publish
    分离方案加列 quality + 改 hp（取自 bjs）120（取自 stable）结构与意图来自 bjs，数值来自 stable

    落到现有模型

    今天
    • base = src r-1
    • source = src r
    • 取值 = src HEAD
    • 写入 = dst HEAD
    →
    分离后
    • base = bjs r-1
    • source = bjs r
    • 取值 = stable HEAD
    • 写入 = publish HEAD

    四版本模型的骨架不变，只是把「定位改动」与「提供取值」两个角色指向不同分支。第 08 章的四条单元格规则可以原样复用，兜底顺序改为 stable → bjs。

    MERGE_RULES.md 单独占了 175 行，全在回答一个问题：
    两组原子操作叠在一起，等于什么。

    先把规格写死、再动手写代码 —— 每条分支都配一个单测，这是这个工具敢反复重构合并逻辑的前提。

    三趟 pass，顺序固定

    1 Header会改写 / 删除 cell 的表头归属
    2 Row会抵消整行的 cell
    3 Cell在前两趟改写后的集合上串接

    A = 较早的累计集合，B = 下一个待并入的集合。每趟结束都跑一次 cleanupCells：丢弃 old == new 的 no-op，折叠完全相同的重复项。
    合并与新建的操作统一落进 B，让 A 保持「较早」、B 保持「较晚」，Cell pass 才能按 newU(A) == oldV(B) 串起来。

    eventual 展开 加/删行或列时，其下每个格子都会展开成一条 cell 操作（删：cur→""；加：""→cur）。
    这条约定把三类操作统一到了 cell 层 —— 下面几个例子几乎都靠它 + Cell pass 串接自动得出结果。

    ① 加行 + 改这行的格子　＝　直接算成新增后的值

    A · r101　加行
    • add 行 5001
    • 展开：[5001,name] ""→"火剑"
    +
    B · r105　改格
    • cell [5001,name] "火剑"→"冰剑"
    =
    结果
    • add 行 5001
    • [5001,name] ""→"冰剑"

    Cell pass (1.1)：newU(A)="火剑" 恰是 oldV(B)，串成 ""→"冰剑"。 界面上只看到一行绿色的新增，name 列写着「冰剑」，没有多余的黄色 modify —— 「火剑」这个中间态从未对外存在过，不该出现在结果里。

    ② 加列 + 填值　＝　同一条规则的另一面

    A　加列
    • add 列 quality
    • 展开：[1001,quality] ""→"S"
    +
    B　改格
    • cell [1001,quality] "S"→"A"
    =
    结果
    • add 列 quality
    • [1001,quality] ""→"A"

    与 ① 结构完全相同。这正是把 eventual 统一到 cell 层的回报：行与列不必各写一套前置规则。

    ③ 加了又删 —— 抵消

    A · r101
    • add 行 5001
    • cell [5001,name] ""→"火剑"
    +
    B · r105
    • delete 行 5001
    =
    结果
    • 全部移除

    Row (2.2)：两条 row 操作对消，同时清掉 A 里该行的全部 cell 操作，并跳过 B 的 eventual 展开。

    ④ rename 接力

    A
    • rename atk→attack
    +
    B
    • rename attack→atk_val
    =
    结果
    • rename atk→atk_val

    Header (2.5)。同时所有 col=attack 的 cell 操作被改写为 col=atk_val。

    ⑤ 类型连改两次 —— 折叠

    A
    • type atk: int→str
    +
    B
    • type atk: str→float
    =
    结果
    • type atk: int→float

    Header (4.4)。若 A 的新类型对不上 B 的旧类型（漏选了中间版本），仍折叠，但记一条告警。

    ⑥ 删 Y + 把 X 改名成 Y —— 最烧脑的一条

    A
    • delete 列 quality
    • cell [1001,quality] "S"→""
    +
    B
    • rename grade→quality
    =
    结果
    • delete 列 grade
    • cell [1001,quality] "S"→"A"

    Header (2.4)：最终消失的是 grade，而 quality 这一列的值换成了原 grade 的内容。 A 里那条 "S"→"" 被改写成 "S"→当前值（当前值取 B 侧版本，此处为 "A"）；A 里没有对应 cell 操作的位置则新建 ""→当前值。此时跳过 eventual 展开。

    ⑦ cell 链式串接

    A
    • cell [1001,hp] "100"→"150"
    +
    B
    • cell [1001,hp] "150"→"200"
    =
    结果
    • cell [1001,hp] "100"→"200"

    Cell (1.1)：newU == oldV 时干净串接。
    若 newU ≠ oldV（漏选了中间版本），仍串成 oldU→newV 并记一条告警。

    ⑧ 删行 ∩ 删列的交点

    同一个 B 内
    • delete 行 1001 ⇒ cell [1001,quality] "S"→""
    • delete 列 quality ⇒ cell [1001,quality] "S"→""
    ⇒
    cleanupCells
    • 折叠为一条

    从两个临时文件反推 SVN URL

    svn 把工具当外部 diff 程序调用时，只递两个 %TEMP% 下的文件路径。

    拿到手的全部信息

    -b C:\Users\X\AppData\Local\Temp\道具表-好感度道具.xlsx-rev2476143.svn000.tmp.xlsx
-m C:\Users\X\AppData\Local\Temp\道具表-好感度道具.xlsx-rev2476144.svn001.tmp.xlsx

    两个文件都在临时目录，都不受 SVN 控制。svn info 对它们无效。

    而工具要画时间线、要拉历史、要做 blame，第一步就得知道这个文件在仓库里的完整 URL。

    唯一的线索：TortoiseSVN 的命名约定

    <原文件名>.xlsx-rev<revision|BASE>.svn<NNN>.tmp.xlsx
    形态含义出现场景
    表.xlsx-revBASE.svn000.tmp.xlsx工作副本的 BASE 导出对未提交的本地改动做 diff
    表.xlsx-rev2476144.svn001.tmp.xlsx某个历史 revision在 svn log 里双击某次提交
    表.xlsx.svn000.tmp.xlsx
    无 rev 段，0 字节    		不存在的那一侧add / delete 记录的 diff

    正则拆出真实文件名与 revision 号 —— 反推的全部起点就是这两样东西。

    三种情形分派

    工作副本mine 不是临时文件且受控 → 直接 svn info，附一个 virtual 节点
    双 revisionbase / mine 都带 rev 号 → 反查 URL，选中两版
    add 记录base 为空文件 + mine 带 rev → 反查 URL，只选中该 rev

    三种都不匹配时直接报错，把收到的 base / mine 原样打出来，方便贴给我们看。

    反查：把 revision 当探针

    实测：svn log -v -r REV <分支根> 只在该 revision 触及该分支时返回 logentry，未触及返回空响应。

    这条性质让「文件属于哪个分支」变成一次廉价的并行试探 —— 拿 revision 号去每个分支根问一句，谁答得上来就是谁。

    两次 revision 求交集去歧

    同一个文件必然被 baseRev 和 mineRev 两次提交同时触及。拿两次 changed-paths 的匹配结果求交集，就能滤掉同名噪音。

    r2476143 触及
    • /trunk/design/道具表-好感度道具.xlsx
    • /trunk/tmp/道具表-好感度道具.xlsx
    ∩
    r2476144 触及
    • /trunk/design/道具表-好感度道具.xlsx
    =
    唯一解
    • /trunk/design/道具表-好感度道具.xlsx

    交集为空说明期间发生过 rename —— 此时回退到较新那次 revision 的匹配结果。

    同名候选的内容消歧

    场景 正常表与它的 _grey 灰度副本被同一次 commit 同时触及，交集里留下两个候选，路径都对得上。
    解法 把候选在 mineRev 上导出，与 mine 临时文件做 sha1 比对。TortoiseSVN 递过来的临时文件就是该 revision 的原始导出，xlsx 字节完全一致。
    1候选 @mineRev 导出 vs mine 临时文件
    2不中则换 base 对再比一次
    3多个候选内容相同 → 任取（diff 结果等价）
    4仍不唯一 → 列出全部候选报错

    三个坑

    A加载界面永久卡死，没有任何报错

    根因
    Electron 里 spawn 的 svn 没有 tty，遇到 auth 提示会静默无限等待，表现为进度条一直转。
    解法
    所有 svn 调用统一加 --non-interactive，再套一层 3 分钟超时，把静默等待转成显式错误。

    B大仓库上 log 输出撑爆缓冲

    根因
    svn log -v --xml 在大型仓库单次输出可超百 MB，一次性缓冲会直接 OOM。
    解法
    流式读 stdout，分块累积，不设缓冲上限。

    C中文路径匹配不上

    根因
    URL 里是 percent 编码，log xml 里是 XML 实体，两层编码叠在一起。
    解法
    统一走 XML 实体解码 → percent 解码 两步，仓库根 URL 只做前缀拼接、不要求可读。

    分支基点列表与仓库根都可用环境变量整体替换（EXCEL_DIFF_SVN_BASES / EXCEL_DIFF_SVN_ROOT / EXCEL_DIFF_WC_SCAN_DIRS），换项目不用改代码。

    缓存体系

    同一张表第二次打开 23.2s → 9.2s。五层缓存，四层落磁盘、跨进程存活。

    前提：revision 内容不可变

    给定 url@rev，字节流永远不会变。
    于是从它派生的一切 —— 导出文件、剥离结果、解析结果、摘要 —— 都可以无限期缓存，不存在一致性问题。整章的每一层都由这一条授权。

    唯一例外 工作副本伪节点（用户本地那份未提交的文件）内容可变。registerRevisionOverride 把它标出来， hasRevisionOverride 在每一层拦掉写缓存 —— 它只走串行解析，永远不入表。

    一次冷启动要付的钱

    五层的 key 与失效

    缓存key位置命中省下失效与上限

    exportsha1(url)/rev磁盘一次 svn export内容不可变，永不失效；30 天未用清理
    stripsha1(路径|大小|mtime)磁盘 24
    内存 3    		读原文件 + 一次注定失败的解析 + JSZip 剥离key 含 size+mtime，源文件一变自然失效
    解析 LRUurl@rev内存一次 exceljs 解析主表 6 + grace 4；随进程结束
    summarysha1(url).json磁盘 + 内存两次导出 + 两次解析 + diff 计算摘要不可变；800ms 防抖合并落盘

    时间线上每个节点的「+3 行 / −1 行」摘要，要解析 r-1 和 r 两个版本才能算出来 —— 解析占其中 97% 的成本，diff 计算只占 3%。所以值得缓存的是摘要结果本身，而不是中间的解析。

    为什么缓存之外还要排队

    exceljs 解析是单线程 CPU 活。交错执行不会更快，只会让每一份都更晚完成。

    队列之上的三条纪律

    做法
    在途合并同一 url@rev 已在解析 → 直接复用那个 promise，不重复排队
    在途升级预取（不入缓存）在途时用户点了同一版 → 就地升级为缓存任务，不解析两遍
    grace 缓存预取结果进容量 4 的旁路小表；用户点到就晋升主表。不进主表是为了不把用户正在看的版本挤出去
    首屏优先 打开文件时用户最关心的是当下选中的那个 diff（通常是「工作副本 vs HEAD」）。 在它构建完成前，时间线的摘要预取整个不放行 —— 曾实测 19.4s 的首屏里有 18s 是在排队等预取让路。

    保留策略：export-cache 的 10 GB

    导出缓存原本只写不删。一台机器上积到 19918 个文件 / 10.1 GB。

    大半不是用户打开过的版本，而是时间线预取为了算摘要顺手导出的 —— 预取半径当时是 ±10，一次滚动就是几十个 svn export。半径已收到 ±5，但存量还得有人清。

    判据：不能用文件系统的 atime

    见下方 case 03。结论是自己盖戳：命中时 utimes 刷新 mtime。revision 内容不可变，mtime 原本只记录「何时导出」、无人读取，可以安全征用成「最后一次用到」。

    环节处置
    触发时机启动后 60 秒。扫两万个文件的 stat 不该跟首屏解析抢 IO
    频率每天一次，靠 .last-prune 标记文件的 mtime 限流
    判据mtime 超过 30 天；顺手收掉因此清空的目录
    并发保护本次会话交出去过的路径记在 inUse 集合里，一律跳过
    失败处置全程 try/catch。清不掉只是占地方，绝不能影响读表

    四个 case

    01摘要把主缓存里现成的版本又解析了一遍

    症状
    日志里 r7681941 先报「workbook 命中」，六行之后又出现「摘要解析 r7681941（不入缓存）」，耗时 2204ms。同一个进程、同一个版本，内存里明明有。
    根因
    查表整体被包在 if (wantCache) 里。摘要路径传 cache:false，于是主表和 grace 两张表都不查，直接排队重解析。cache:false 的本意是「别污染 LRU」，却被写成了「别用缓存」。
    解法
    把查表和副作用拆开。命中一律复用；wantCache 只决定要不要刷新 LRU 次序、要不要把 grace 晋升主表 —— 预取不该扰动用户正在看的那几版。
    // revision 内容不可变 → 已解析结果一律复用，与是否入缓存无关
const hit = wantCache ? lruGet(cache, key) : cache.get(key);
if (hit) return hit;              // 差别只在「要不要动 LRU 次序」

    02剥离缓存把 5.2MB 的表写成 61.5MB

    症状
    加完磁盘缓存后去 %APPDATA% 看了一眼，单个条目 61.5MB。按当时 40 个的上限，光这一层就能占 2.4GB；内存 LRU(3) 还常驻 184MB。
    根因
    JSZip 的 generateAsync({type:"nodebuffer"}) 默认是 STORE，不压缩。xlsx 本身就是 DEFLATE 过的 zip，剥离后重新打包等于把整包 XML 摊平了写回去。
    解法
    显式指定压缩，上限 40 → 24。剥离本来就只发生一次，那一次的压缩成本完全可以忽略。
    return await zip.generateAsync({
  type: "nodebuffer",
  compression: "DEFLATE",           // 默认 STORE，必须显式指定
  compressionOptions: { level: 3 }, // 只在剥离时付一次
});

    03拿文件系统 atime 当「最后一次用到」不可行

    症状
    要给 export-cache 加保留策略，第一反应是读 atime —— 操作系统已经在记「最后访问时间」了，何必自己造。
    根因
    NTFS 的 atime 不可信。本机查出来是 DisableLastAccess = 2（更新开启），可实际值全是坏的：
    文件mtime（导出时间）atime
    1287747-衣柜配置表.xlsx02-19 14:2708-06 19:33
    1292671-衣柜配置表.xlsx02-22 16:3308-06 19:33
    1308106-衣柜配置表.xlsx03-02 18:0008-06 19:33
    1308268-衣柜配置表.xlsx03-02 19:0608-06 19:33

    前后跨了半个月导出的文件，atime 全是同一个值 —— 某次杀软 / 备份 / 索引器整树扫了一遍，把所有 atime 一次性抹平。 任何批量读文件的程序都会毁掉这个信号；何况 NTFS 的 atime 写入还有最长 1 小时延迟，各台机器的注册表默认值也不一致。

    解法
    自己盖戳：命中时 utimes 刷 mtime。只有我们自己写的时间戳，语义才由我们说了算。

    04损坏的缓存条目没有退路

    隐患
    尚未在线上出现，是加完磁盘缓存后复查代码时发现的：半截写入或磁盘错误产生的 strip-cache 条目，会让这份表永远打不开 —— 每次读都取到同一个坏 buffer，exceljs 抛错直接冒泡给调用方。比没有缓存更糟。
    根因
    写入侧做了「临时文件 + rename」防半截，读取侧却无条件信任读回的字节。防御做了一半。
    解法
    装载缓存 buffer 的那次 load 单独 try/catch：失败即删条目（内存 + 磁盘），回退到读原文件重新剥离。回归测试直接塞一个非 zip 的 buffer 进去，断言仍能读出正确数据、且坏条目被删除。
    下一步 缓存能省的都省完了，剩下的地板是首次打开必须串行解析的那 2–3 个版本。 已量过 worker_threads：3 版串行 8.79s，3 个 worker 并行 4.63s（1.9×），结构化克隆传回 300 万格约 0.75s，可以接受。 没有立刻做 —— 相比之下缓存这几层的收益更大、风险更低。

    历史日志：150MB 换几个角标

    上一章用缓存把 11.5s 的历史加载藏了起来，但没让它变快。去掉一个 -v 参数：传输量 150.30MB → 0.64MB。

    被缓存挡住的那根柱子

    图 6-1 最左边那根是 svn log -v：11.5s。上一章给它加了 history-cache，于是它只在首次出现 —— 然后就没人再看它了。

    但「首次」不是罕见情况。用户打开一张没看过的表时付的正是这个价，而这恰恰是最常见的入口。 缓存把问题移出了视线，没有移出代价。

    串在关键路径上 视图构建整个挂在 history 上（diff effect 开头就是 if (!history) return）， 而文件打开的 effect 要等 getHistory 回来才设默认选中版本。 这 11.5s 完全是串行的，期间界面上什么都没有。

    -v 到底买到了什么

    -v 会给每一个 revision 附上那次提交的全部 changed paths。 一次触及三千个文件的提交就要传三千行 —— 而我们只关心其中一个文件。

    这些字节的去向用途
    <paths>唯一的消费者是 resolveChangeType
    changeType时间线圆点上的 A / D / R 角标；R（replace）之后的连线变色
    其余没有了。

    diff 本身根本不看节点列表：基线版本是 rev - 1 直接算出来的，svn export url@rev-1 在任意版本都成立。 节点列表只服务于时间线渲染、blame 的版本区间，以及「跳过了中间版本」的告警。

    一个被实测否决的方案

    最先想到的是分阶段拉取：先只拉选中版本和它的前一版，把 diff 画出来；再拉 ±5 个节点补摘要；最后后台拉全量。时间线未到货的部分先置灰。

    思路没错，首屏确实能快。但动手前先量了一轮，读数把它否了。

    命令svn 耗时传输节点
    Alog -v --xml　全量（原实现）2758ms150.30 MB2858
    Blog --xml　全量，去掉 -v261ms0.64 MB2858
    Clog -v --limit 2　阶段 1124ms~4 KB2
    Dlog -v --limit 11　阶段 2125ms12 KB11
    Elog -v -r R:1 --limit 2　锚定任意版本146ms~4 KB2

    同一个文件，2858 个 revision，局域网。

    读数推论
    C ≈ D（124 / 125ms）成本在往返，不在条数。阶段 1 和阶段 2 一样贵 → 它们本该是一次调用
    B = 261ms，节点全不分阶段也能拿到完整列表，只比阶段 1 多 137ms —— 分阶段的全部复杂度，只换这 137ms
    结论 只做 B。2758ms → 261ms，列表仍然是完整的，不引入任何「半截状态」。 分阶段留到 261ms 也嫌慢的那天再说 —— 目前不嫌。

    半截列表的三处暗礁

    如果当时真按分阶段做了，下面三处会静悄悄地错，而且都不会报错：

    位置会发生什么
    blame 版本区间blame 拿全部节点的 revision 去溯源。半截列表会让它只扫已拉到的那几版，追不到真正的改动者
    创建点标记时间线把「最老的一条」画成文件创建点。列表半截时，最老的已加载节点会被画上一个假的创建标记
    跳版告警「你跳过了中间 N 个版本」要靠完整列表算，半截时漏报

    三处都得靠一个 partial 标志逐个绕开，而且每一处错得都很安静。省下的 137ms 买不起这些。

    降级安全吗

    去掉 -v 后 <paths> 不再返回，解析代码一行没改，自然降级。

    原行为现行为
    resolveChangeType 扫 <path>扫不到 → 一律返回 { type: "M", matched: false }
    最老一条的创建点修正matched=false 正是它原本的触发条件 → 最老一条仍标 A
    A / D / R 角标丢失：除创建点外全是 M，R 之后的连线不再变色

    最老一条标 A 是对的：全量查询会追随 copy 链一直回到文件历史的起点，那一条本来就是创建点。 分支探测用的 logMatches 保留 -v —— 它是真要读 changed paths 才能在分支间定位文件，而且只查单个 revision，很便宜。
